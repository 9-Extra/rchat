# 编写 RChat 世界包

RChat文字冒险/角色扮演框架的世界包类似跑团规则书，记录一个世界的各种世界观，规则，剧情背景，文风指导，数值算法等等信息供AI GM查阅。
世界包是一组结构化的文档：RChat开局时自动上下文注入入口文档全文作为基础，然后AI通过索引按需使用 read_file （工具调用）读取细节文件。
规则编写自由：数值相关规则可以用自然语言、伪代码或代码片段写，可以包含复杂/大数字计算。告诉 AI 要追踪什么状态、如何计算，AI 自行用 world_run 写代码完成初始化、判定与更新。
详细的计算规则会使 AI 严格遵循，模糊描述则 AI 会灵活裁量，编造数值和公式（合适时可以这么做，留白也是一门艺术）。
AI具有充分的基础知识和能力，不需要提示它“掷骰必须写代码”或者“你需要用read_file读取文档”。

## 入口文档特殊格式

一级目录下唯一的一个文档为入口文档，框架会对其中的<game_setting>，<user_setting>和<game_beginning>使用预处理规则拼接AI的初始上下文，没有被块包裹的内容对AI不可见。实例格式如下：
```markdown
---
name: 幽暗森林
description: 低魔奇幻求生世界
---
<game_setting>
# 世界观
（基调、常识、势力轮廓——叙事依据，只写每个回合都可能影响演绎的部分。此部分可能较长并且分为多个小节，非常细节冗长的设定可以划入别的文档）

# 状态清单
（AI 照此在 world_run 初始化状态记录。每字段写清：名称、初始值、取值范围/单位、更新时机。例：）
- 生命值 hp：初始 50，0–50，受伤/治疗时更新
- 体力 sp：初始 30，0–30，冲刺/战斗消耗，每休息 1 小时恢复 10
- 金币、物品栏（含重量；负重上限 = 力量 × 5）
- 游戏内时间（回合制，1 回合 = 10 分钟）

以下是一些状态设计的建议，到底什么需要数值化存在决策空间，模糊叙事和精确数值各有用处，建议与用户讨论。
什么应该记录到状态内：
- 需要计算的数值
- 需要数值化的状态
- 明确的阶段性的内容
- 需要减少叙事模糊性的内容，比如将好感度数值化则角色爱上你就一定爱上你

什么不应该记录到状态内：
- 文档里有的信息（比如角色的人设性格）
- 在叙事正文中普遍存在的信息（比如角色的情绪）
- 剧情日志（上下文本身就是）
- 需要留下灵活叙事空间的内容，非数值化意味着AI自由发挥空间更大，角色是否真的爱上你可能出现反转
- 什么状态都不记，AI完全自由发挥都是可以的，传统AIRP就是这么做的


# 判定规则
（核心判定写到可计算的程度：公式、骰子表达式、阈值表。例：潜行判定 = d20 + 敏捷修正 ≥ 目标警觉值。冷门判定拆分。可以直接写伪代码或者代码）

# 触发器表
（"条件 → 效果/提醒"清单，GM 开局翻译成 normalize 整理函数。例：hp ≤ 12 → 提醒"濒死：全判定 -2"。）

# 索引
| 文件 | 内容预告 |
| 规则/战斗.md | 战斗时的先攻、攻击/伤害公式、状态异常 |
| 规则/社交.md | 与 NPC 交涉时的好感度判定与价目 |
| 规则/通用设定.md | 背景设定，术语与年表（前置阅读） |
| 秘密/密室.md | 密室的秘密，仅当玩家发现密室后阅读 |
</game_setting>

<user_setting>
（玩家扮演的角色设定，可以详细写这里，也可以只放一句：用户扮演xxx，或者写“由AI开局时引导玩家生成”）
（如果开局有多个玩家设定，可以留空，然后把设定全部写到开局内）
</user_setting>

<game_beginning>
（开局信息：初始场景、初始状态、开场氛围、开局故事）
</game_beginning>
<game_beginning>
（开局可以有0个或多个）
</game_beginning>
```

其他文档都是普通的文本文件，没有任何框架层面的格式要求，通常使用md方便AI阅读，也可以看情况其他格式，比如csv、yaml甚至py。

## 信息量预算

- **入口文档必然被完整读取**：放每个回合都可能用到的东西——基调、简要通用信息、状态清单、核心判定规则、索引。
- **二级目录内的文档按需读取**：一切有触发条件/不是所有情况都需要的内容（NPC，物品表、法术列表、地点详情、特殊分支、秘密）都该放这里。
- 对于势力，种族等通用信息，如果比较详细冗长，则策略是在入口文档写简介，让AI知道它的存在和大致情况，然后将玩家深入接触时才需要的详细信息放入二级目录的文档中按需调取。

## 索引

1. **完整索引（防"找不到"）**：告诉 AI "存在这个文件、什么时候读它"，格式为 `文件 | 一句话内容预告（让AI知道什么时候读它）`。框架没有给AI枚举文件（ls）能力，因此所有二级目录内的文档都必须有索引和相对入口文档目录的完整路径，否则AI找不到。
2. **触发器表（防"忘了查"）**：把"当 X 时自动 Y / 提醒 Z"集中成一张清单（如"hp ≤ 上限25% 时提醒濒死状态""每日黎明结算补给消耗"）。AI 开局会把它翻译成 world_run 的 normalize 整理函数（每次执行后自动调用一次），此后由代码保证触发，不再依赖上下文记忆。条件式规则尽量收成这张表，而不是散在各章节里。

## 定位效率：按触发场景拆分，而非按设定类别

- 一个场景一个文件：按"什么时候需要它"分（战斗.md、社交.md、旅行.md、交易.md、升级.md……），不按设定类别分（地理.md、历史.md）。最好让AI一次查找只读一个文件，读到的全是当前场景的有效信息。
- 细粒度拆分：如果信息不需要整体读取，比如有50个NPC设定且每个都很长，而且通常AI只需要其中几个的设定，则可以每个NPC都单独拆成一个文件。
- 自包含：让AI不需要递归读取多个，只读一个文件就足以裁决对应场景。
- 同一规则只定义一处：其他地方用指针。重复既费 token，又在改动时制造不一致。
- 剧透隔离：未揭示的真相、隐藏支线、反派的真实动机等单独成文件，索引中标注"仅当 X 发生后阅读"。AI 读过的内容会渗进叙事；没读过就不会剧透——按需隔离既省 token，也是防剧透机制。

## 内容编写策略

世界包的内容都是AI提示词，遵循一般的提示词编写技巧，保证简洁，清晰，结构化。
AI永远没有看过“旧版本文档”，不需要告诉它什么发生了修改，只需要写最新的信息。
慎用"不是...而是..."进行强调，是什么就是什么，除非这真的很容易误解，否则删除"不是"的部分。
AI具有推理能力，如果某项规则本就模凌两可，详细展开显得冗杂，可以直接留白不写交给AI自行判断。

## 交付前自检

- 随便想 5 个玩家可能的行为，每个都能在索引里一步找到入口？
- 随机抽一个引用文件，只读它一个就够裁决对应场景？
- 同一规则是否只定义了一处？
- 所有条件式规则是否都收进了触发器表？
- 所有剧透内容是否都标了"仅当 X 后阅读"？
- 逐段检查入口文档：有没有哪段不是每个回合都用得上？有就拆出去。
